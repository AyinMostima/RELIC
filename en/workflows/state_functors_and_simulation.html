State, Functors, and Simulation

The executable RELIC lifecycle has one state owner and one simulation owner. StateManager validates and commits tensors. Scientific Functors calculate UpdateItem objects. RELICSimulator orders Functors, supplies time and device context, commits each group call’s updates through StateManager, and wraps all group commits of a step in one accepted-step transaction.

Parameter

Meaning

value

Tensor or tensor-compatible value to commit.

mode

ACCUMULATE, REPLACE, or FLUX.

write_mode

Optional update-side write policy override.

unit

Units of value; the manager converts compatible units to the schema unit.

basis

Legacy integration basis, per_step or per_second.

per_timestep

element

Optional conservation-ledger element such as carbon or water.

Writer identity for provenance and conflict accounting.

New code should state per_timestep explicitly. A per_second update requires dt. Unsupported basis values, unknown variables, incompatible units, or write-policy violations raise an exception before a valid commit is accepted.

Use get_state(clone=False) only for performance-critical read-only access. The canonical simulation update path is apply_updates(), not direct mutation of tensors returned by the manager. checkpoint()/restore() are full in-memory snapshots used by the adaptive retry and embedded in the durable simulator checkpoint; the accepted-step rollback uses create_transaction_savepoint()/restore_transaction_savepoint(). Neither is a second file format or an independently durable persistence system.

import torch
from relic.core.state import StateManager
from relic.core.state.types import StateVariableSpec, UpdateItem, UpdateMode

manager = StateManager(
    {
        "carbon_pool": StateVariableSpec(
            name="carbon_pool",
            units="kg C m-2",
            bounds=(0.0, 100.0),
            conserved=True,
            accumulates="carbon.total",
        )
    }
)
manager.initialize({"carbon_pool": torch.tensor(2.0)})
snapshot = manager.checkpoint()

manager.apply_updates(
    {
        "carbon_pool": UpdateItem(
            value=torch.tensor(0.25),
            mode=UpdateMode.ACCUMULATE,
            unit="kg C m-2",
            per_timestep=True,
            element="carbon",
            source_functor="documented_input",
        )
    },
    dt=3600.0,
    check_conservation=False,
)
manager.restore(snapshot)
print(float(manager.get_state()["carbon_pool"]))

Expected output:

2.0

FunctorBase and bridge classes

Every executable scientific process follows:

scientific abstraction -> bridge class -> FunctorBase -> parameter system

Spatial or temporal physical fields.

Biological transformations and rates.

TransportMechanism

TransportMechanismFunctor

Advective, diffusive, or managed transport.

ScaleCoupling

ScaleCouplingFunctor

Concrete Functors implement:

forward(
    state: dict[str, torch.Tensor],
    time: float,
    dt: float,
    **kwargs,
) -> dict[str, UpdateItem]

The state mapping is an execution snapshot. time and dt always describe the same real interval. A group call covers [t_s, t_s + dt_group]; with h_sub = dt_group / substep_count, sub-step k (counting from 0) receives time = t_s + k * h_sub and dt = h_sub. The start t_s and the length dt_group depend on the call:

  • fast group in lie mode: t_s is the step start and dt_group is the step length h;

  • strang mode with two or more fast Functors: the first half-steps (dt_group = h/2) and the middle full step of the last fast Functor (dt_group = h) start at the step start, and the second half-steps (dt_group = h/2) start at the step start plus h/2;

  • medium or slow group: t_s is the group’s last execution time t_last and dt_group = t_future - t_last, where t_future is the end of the current step. A non-positive dt_group raises RuntimeError.

For example, with t_last = 0 and a step from 1 s to 2 s, a medium call receives time = 0 and dt = 2, the interval [0, 2] that it accounts for; t_last then becomes 2. dt never starts before time.

The result maps names to state updates, diagnostics (diagnostics.* names or DERIVED outputs), or top-level ExternalIntent requests; the simulator commits only the state updates and delivers requests after the step is accepted. A Functor must not mutate shared state directly or call another Functor as a hidden dependency.

FunctorMetadata

Metadata is the executable contract used for dependency ordering, scale detection, validation, provenance, and structural compilation.

Metadata group

Important fields

name, version, description, category, execution_phase

Science

mathematical_expression, references, parameters, conservation_laws

Data contract

Scale and scheduling

spatial_dimensions, spatial_scale, temporal_scale, variable_kind, substep_count, sub_flow_accuracy

form_contracts, hodge_contracts, iphs_terms, stoichiometric_contracts, structural_role

Concurrency

asynchronous capability (async_safe, stream_hint: declarations only; the simulator runs Functors sequentially) and conflict_resolution_policy (enforced for output overlaps at registration)

optional_output_variables must be a sequence of names (not a string), a subset of output_variables, and free of duplicates. spatial_dimensions must be 0, 1, 2, or 3, and substep_count must be at least 1; the simulator splits each group interval into substep_count sub-steps.

Execution-order dependencies are not a FunctorMetadata field. They are declared on the Functor instance through config["dependencies"] (a list or a single name), set_dependencies(...), add_dependency(...), and remove_dependency(...), and exposed by get_dependencies(), which returns a list or a mapping with required, optional, and lagged keys. A class that adds a static declaration returns self._merge_declared_dependencies(static), so the instance names are merged with it without being dropped.

Declare both spatial_scale and variable_kind. Empty input and output declarations generate a warning when the FunctorMetadata object is constructed, normally in the Functor’s __init__ and therefore before registration; registration itself does not issue this warning. Diagnostic outputs use the diagnostics.* namespace when they should not participate in ordinary output overlap ownership.

RELICSimulator

RELICSimulator(config: Optional[dict[str, Any]] = None)

Provenance mapping

Execution groups are fast, medium, and slow. The group follows one priority chain: the execution_group argument, the Functor attribute, the characteristic time, the temporal scale, process_groups, and fast only when nothing is declared. An invalid declaration, or a process_groups entry that contradicts the attribute, the characteristic time, or the temporal scale, raises ValueError before anything is registered; the argument overrides the entry. The simulator derives dependency order separately for each group. Declared cross-group reads are checked each time a provider view is published (registration, retirement, or restore), not on every step, and in both directions. A slower consumer that reads a faster group’s declared output gets the warning “Cross-group sampling lag”. A faster consumer that reads a slower group’s output, for example a fast Functor reading a medium or slow output, gets “Cross-group hold lag”: it holds the value committed when the producer last ran. Listing the producer in the consumer’s lagged dependencies acknowledges the read, which is then logged only at debug level. With strict_cross_group_dependencies=True (a bool, default False) any unacknowledged read raises RuntimeError and the publication is rolled back. With resolve_cross_group_deps=True, slow consumers with an unacknowledged sampling lag are first moved to the medium group; nothing is moved into the fast group.

Registration rules

  • The object must inherit from FunctorBase; otherwise TypeError is raised.

  • Functor names must be unique; duplicates raise ValueError.

  • A concrete scientific Functor should inherit through the matching bridge.

  • Critical state-output conflicts and mutually exclusive writers raise ValueError.

  • Ordinary output overlaps warn by default and can be escalated with strict_dependencies=True.

  • Device migration occurs at registration, after the Functor’s initial CPU placeholder has been created.

step() promotes INITIALIZED to RUNNING. A failed step restores the StateManager savepoint, simulator step bookkeeping, Functor state_dict() and extra state, random number generator (RNG) states, and the provenance transaction before re-raising; it does not undo external files or services. A failed run() sets the simulator state to FAILED and re-raises the exception. Stateless execution is not a supported normal path.

Checkpoint ownership and boundaries

relic\core\simulator\checkpoint.py is the only durable checkpoint owner. Manual creation without a snapshot requires an explicit non-existing path; there is no implicit destination and no public cleanup API. Automatic checkpointing defaults to off and requires enable_checkpointing=True, an explicit checkpoint_directory, and a positive checkpoint_frequency. Automatic files are committed atomically after accepted scientific and provenance step state has committed.

The strict relic.simulator.checkpoint format writes format_version=3 and is restored with weights_only=True. Each Functor entry has state_dict (including safe PyTorch extra state) and parameter_bindings for live values held by reference from its manager. Version 2 is upgraded in memory with a format_upgrade restore receipt. Binding restoration checks key sets, shapes, and dtypes and preserves live identity, gradient flags, and devices. The payload binds StateManager state, these Functor entries, scientific/topology/parameter contracts, resolved device and distributed signatures, and Python, Torch CPU, legacy global NumPy, and symmetric CUDA RNG states. The current single-file format rejects an active world_size > 1. Create and restore return receipts with path, format version, size, file hash, and payload hash; restore compensates in-memory owners only before provider-view publication. After publication, retirement or receipt errors preserve the committed scientific state and new epoch while reporting the failure.

A Functor with replay-critical mutable data outside parameters and buffers implements get_extra_state() and set_extra_state() so that PyTorch owns the extension through state_dict(). It must not add another checkpoint API. Bitwise equality from a continuous/restart test is evidence for that exact graph, input, fixed-step, dependency, and device setup, not a cross-platform guarantee.

Complete minimal example

import torch

from relic.core.dependency_graph import DependencyGraphResolver
from relic.core.functor import BiologicalProcessFunctor, FunctorMetadata
from relic.core.functor.functor_types import (
    ProcessCategory,
    SpatialScale,
    VariableKind,
)
from relic.core.simulator import RELICSimulator
from relic.core.state import StateManager
from relic.core.state.types import StateVariableSpec, UpdateItem, UpdateMode


class IncrementFunctor(BiologicalProcessFunctor):
    def __init__(self):
        metadata = FunctorMetadata(
            name="increment",
            description="Minimal state increment example.",
            category=ProcessCategory.BIOLOGICAL_PROCESS,
            mathematical_expression="x_next = x + 1",
            references=["Executable documentation example"],
            input_variables=["x"],
            output_variables=["x"],
            spatial_scale=SpatialScale.POINT,
            variable_kind=VariableKind.STATE,
        )
        super().__init__(name="increment", config={}, metadata=metadata)

    def forward(self, state, time, dt, **kwargs):
        return {
            "x": UpdateItem(
                value=torch.ones_like(state["x"]),
                mode=UpdateMode.ACCUMULATE,
                unit="dimensionless",
                per_timestep=True,
                source_functor=self.name,
            )
        }


manager = StateManager(
    {"x": StateVariableSpec(name="x", units="dimensionless")}
)
manager.initialize({"x": torch.tensor(1.0)})

simulator = RELICSimulator({"time_step": 60.0})
simulator.initialize(manager, DependencyGraphResolver())
simulator.register_functor(IncrementFunctor(), execution_group="fast")

updates = simulator.step(60.0)
print(float(simulator.get_state()["x"]))
print(sorted(updates))
print(simulator.step_count)

1
